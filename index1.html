    Setting Up a SOC Home Lab as a Beginner

    Table of contents

    • What this topic means
    • Why it matters in SOC work
    • A simple lab layout
    • Tools and evidence to review
    • Attacks to practice first
    • Beginner notes
    • Key takeaways

    What this topic means

    A SOC home lab is a small, isolated network of virtual machines where you create security events on purpose, collect the logs in one place and practice spotting them. It is a scaled-down version of what a security operations center does every day.

    Why it matters in SOC work

    An alert only makes sense once you have seen the activity behind it. In a lab you can run a port scan or a brute-force attempt yourself and then watch what it looks like in the logs. You learn which log source shows what, you can write and test detections without risking a real system, and you build proof of hands-on work that a certificate alone cannot show.

    A simple lab layout

    The layout in my SOC-Homelab-Setup repository uses four machines on one isolated virtual network:

    • Attacker: Kali Linux, used to run Nmap scans and brute-force attempts.
    • Windows 11 endpoint: runs Sysmon and a log agent, and forwards Windows event logs, PowerShell logs and Sysmon data.
    • Windows Server: a second endpoint that forwards system and security logs.
    • SIEM server: an Ubuntu Server that collects, indexes and displays the logs from every endpoint.

    Tools and evidence to review

    Kali Linux and Nmap generate the activity. Sysmon adds detailed Windows telemetry. The SIEM lets you search the logs and build alerts, and MITRE ATT&CK gives you a shared language for labeling what you find.

    The evidence worth reviewing is process creation events, network connections, authentication events and PowerShell command lines.

    Attacks to practice first

    Four simulations are enough to start, each with its MITRE ATT&CK technique:

    • SSH or RDP brute force (T1110): look for a burst of failed logins from one source.
    • Nmap port scan (T1046): look for one source touching many ports in a short time.
    • Suspicious PowerShell and encoded commands (T1059.001): look for long, encoded command lines in PowerShell and process creation logs.
    • New user creation and privilege escalation (T1136 and T1068): look for new accounts and accounts added to privileged groups.

    Beginner notes

    • Keep the lab network isolated from your home network.
    • Take a snapshot of each virtual machine before you run an attack.
    • Write down the exact time and command of every test, so you can find it in the logs afterwards.
    • Add one log source at a time and confirm it arrives before adding the next.
    • Screenshot each detection and write it up like a small case.

    Key takeaways

    • A lab turns abstract alerts into activity you recognize.
    • Start small: one attacker, one endpoint and one SIEM.
    • Documenting every exercise is what turns practice into portfolio evidence.

    SSH Brute-Force Detection Using Ubuntu

    Table of contents

    • What this topic means
    • Why it matters in SOC work
    • Tools and evidence to review
    • My detection rule
    • What I found in my lab
    • Beginner notes
    • Key takeaways

    What this topic means

    An SSH brute-force attack is a run of repeated failed login attempts against a Linux server, usually guessing passwords for one or more accounts. On Ubuntu, the SSH service writes every attempt to the authentication log, so the evidence is already there for an analyst to read.

    Why it matters in SOC work

    Brute force is a common first step for attackers and maps to MITRE ATT&CK technique T1110 under Credential Access. Analysts review the volume of failures, the source IP, the targeted usernames, the timestamps and, most importantly, whether any login succeeded after the failures.

    Tools and evidence to review

    My lab used Ubuntu running under WSL, OpenSSH Server and Python 3. The main evidence is the file /var/log/auth.log.

    • Source IP address of each failed attempt
    • Username that was targeted
    • Timestamps and how many attempts fall inside a short window
    • Any successful login that follows the failures

    My detection rule

    I wrote two Python detectors. The first counts failed logins. The second looks at a time window, and it raises a HIGH severity alert when one source IP has five or more failed SSH attempts within 60 seconds.

    What I found in my lab

    The detector raised a "Possible SSH Brute-Force Attack" alert. When I investigated it, the source was 127.0.0.1, which is the machine itself, and there were 6 failed attempts against one username inside 53 seconds. I found no successful SSH login.

    I mapped the activity to Credential Access, T1110.001 (password guessing), and classified it as benign, because I had generated the failed logins on purpose as part of a controlled lab. I then wrote an incident report covering the alert, the investigation and the MITRE mapping.

    Beginner notes

    • Start with who, what, when, where and how many attempts.
    • Always check for a successful login after the failures. Failures alone are noise, while a success after failures needs escalation.
    • A source of 127.0.0.1 tells a very different story from an unknown external address, so note where the traffic came from.
    • Thresholds need tuning. Five failures in 60 seconds suited my lab, but a real environment may need different numbers.

    Next on my list are GeoIP enrichment for external addresses and sending the alerts into Splunk or Wazuh.

    Key takeaways

    • A spike in failed logins needs context before it becomes an incident.
    • A successful login after repeated failures raises the severity.
    • Clear documentation makes escalation faster for the next analyst.

    How I Investigate a Phishing Email

    Table of contents

    • What this topic means
    • Why it matters in SOC work
    • Tools and evidence to review
    • What I looked for in my sample
    • Beginner notes
    • Key takeaways

    What this topic means

    A phishing email pretends to come from someone trustworthy and tries to get the reader to click a link, open an attachment or hand over a password. Investigating one means deciding, with evidence, whether the message is malicious and what should happen next.

    Why it matters in SOC work

    Email is one of the most common ways attackers reach people, and reported emails land in the SOC queue every day. A good analyst gives a fast, clear verdict and records the indicators of compromise so the same message can be blocked everywhere.

    Tools and evidence to review

    • Sender details: the display name, the real sender address and the reply-to address.
    • Email headers: the path the message took and its SPF, DKIM and DMARC results.
    • Links: where each one really points, checked without clicking.
    • Attachments: the file name, type and hash.
    • VirusTotal: to check the reputation of links, domains and file hashes.

    What I looked for in my sample

    I went through a phishing email sample in a text editor and picked out the signs it was malicious: a fake sender address, a suspicious URL, urgent wording that pressures the reader to act, a malicious attachment and general social engineering tactics. My verdict was phishing, and I wrote up the findings in my repository.

    Beginner notes

    • Never click links or open attachments from the email on your normal machine.
    • Defang indicators when you write them down, for example hxxp://example[.]com, so nobody clicks them by accident.
    • Compare the display name with the real address, because attackers often fake only the name.
    • Finish with an action as well as a verdict: block the sender and the link, remove the email from other mailboxes, and reset the password if someone clicked.

    Key takeaways

    • Check the sender, the links, the attachment and the wording, in that order.
    • Record every indicator so it can be blocked.
    • A clear verdict and next action help the team respond faster.
